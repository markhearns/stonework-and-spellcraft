# Codex task — integrate selected expansion content safely

Read this kit’s README, `reference/00-shared-contract.md`, `reference/prototype-reference.json`, `PACK-INDEX.md`, and the selected pack’s manifest, numbered handoff, README, validation report, and `CODEX-HANDOFF.md`. Implement against the actual repository. This delivery supplies data, not permission to invent an engine or auto-enable every proposed rule.

## 1. Establish the repository boundary

Inspect the existing foundations importer, schemas, save versions, actor/room/item models, assignment logic, personal knowledge, preparation, and test suite. Determine what actually exists. The handoff snapshot says only foundations currently import; do not assume either that statement or newer expansion support without checking code.

Preserve existing accepted characters and saves. Eris and Selene are external players, not GM-controlled NPCs. Do not author their actions, feelings, agreement, or resource spending. Preserve independent adult resident agency and the original twenty-one-ancestry identity pool.

## 2. Add data support before effect support

Validate the selected pack with all real dependencies. Add strict record-type parsing with schema/version checks, exact field sets, global IDs, tags, ancestry filters, reference namespaces, and dependency validation. Reject unknown effects and extra keys. Missing dependencies block activation; they are not replaced with invented IDs or discarded silently.

Keep narrative candidates separate from accepted save facts. Fact requirements are non-executable eligibility metadata. Choice results, letters, invitations, relationship developments, and future discoveries require actual play and current permission. A public-template label is not permission to reveal an undiscovered clue.

Provide a review view for mechanics-proposal data, disabled by default. Do not build a generic interpreter for English effects or execute commands, formulas, scripts, or model instructions from content strings.

## 3. Implement only explicitly selected mechanics

For each selected mechanic, resolve unknown costs, durations, quantities, ownership, preparation, and supported targets. Compare its balance with the actual baseline. Implement it as typed, allowlisted application code, with tests. Leave the rest as visible proposals. List unresolved decisions rather than interpreting null as zero or unlimited.

Preserve one primary assignment per person, explicit human Advance, no offline progress, source-linked personal knowledge, actual preparation slots, and ordinary free conversation/decorating. Functional work still needs supported costs and phases. Separate personal and shared wallets, equipment ownership, room installation, and worker assignments.

Important cross-pack interactions: pack 17’s six narrow +1 fabrication perks use a single alternative support contribution alongside pack 06 adjacency support and baseline binding-press; do not sum that support channel. Baseline personal practices are otherwise unchanged. Starter proposals preserve zero ranks, no earned advancement, one focus slot, and only independently chosen limited knowledge. Golem vocations remain prospective, with capabilities established through actual post-awakening learning rather than inferred careers or body materials.

## 4. Preserve safety and continuity in the data model

Refusal and deferred invitations have no hidden relationship penalty or expiration. No consent, loyalty, obedience, or romance meter is introduced. No service, food, gift, room, or attractive appearance grants or spends Resonance. Care, accommodation, work, finances, and intimacy remain independent choices.

Safe withdrawal from contact, augmentation, or care must never wait for optional aftercare work, money, labour, or affection. Ordinary underground bedrooms are not containment. Restored living areas remain sanctuary; do not add random raids, attention decay, or compulsory jealousy.

Preserve existing recipe and spell receipts and do not pay an existing output twice through a commission. Imported materials are definitions, not free inventory. A material property name is not an automatic engine capability. Do not treat an archive principle as everyone’s personal mastery.

## 5. Make changes transactional and testable

Use stable operation IDs and atomic receipts for scheduling, consumed inputs, completed stages, rewards, acquisition, cancellation, and migration. Test repeated requests, stale tabs, save/reload, actor departure, missing inputs, owner changes, failed prerequisites, inaccessible controls, and cancellation at every stage. Reconcile actual ownership on refunds; never mint replacements for already consumed inputs without an explicitly reviewed rule.

Use pack 16’s sixty-four integration scenarios as specifications. Implement and run the relevant repository tests; do not report the written scenarios as already passing. Add keyboard, focus, readable unavailable-state explanations, and assistive-technology checks where applicable.

## 6. Keep pack 13 private and optional

The public bundle intentionally excludes its generated contents and has no dependency on it. Do not fetch or load it as ordinary context. A private future-campaign tool may review alternatives, select at most one after deliberate approval, and store the choice separately. Never retcon an active campaign, combine alternatives into one history, or disclose private premises in client assets, logs, indexes, or routine implementation reports.

## 7. Return an evidence-based implementation report

Report changed files, imported record types and counts, explicitly enabled mechanics versus still-disabled proposals, migration strategy, tests actually executed and their results, and remaining design decisions. Do not claim runtime support from a successful data validation alone. Do not rename stable IDs or overwrite foundation content as a convenience.
